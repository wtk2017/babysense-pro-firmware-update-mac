# How it works (technical notes)

This page explains how the Babysense Pro parent unit receives a firmware update, why a Mac
cannot do it out of the box, and what this tool does instead. Everything here was observed on
a real Babysense Pro (MaxView Pro) parent unit or read out of Babysense's own updater package.

## The parent unit over USB

| What | Value |
|---|---|
| USB vendor/product | `0c45:8801` (SONiX), product string `SN93701PU`, USB 2.0 high speed |
| USB class | Mass storage, SCSI transparent, Bulk-Only Transport (endpoints `0x8C` in, `0x0D` out) |
| SCSI identity | vendor `SONiXTek`, product `510PF`, revision `rev1`, removable |
| Capacity | 990,400 sectors × 512 bytes (507 MB) |
| Filesystem | FAT16, no partition table, 16 sectors per cluster, 2 FATs of 242 sectors, 512 root entries |
| Root folder | volume label `SN93701PU` and an empty entry named `01.00.01.051` |

The parent unit only appears on USB while it is switched on. In the battery-warning state it
switches itself off a little later, which is why the tool waits for it and asks you to turn it on.

## Why macOS can't use the drive

When the parent unit connects, macOS attaches its normal USB storage driver. The device stalls
one of the driver's first commands, macOS retries for about eight seconds, then unloads its
disk driver. No disk ever appears in Finder or Disk Utility, and Disk Utility can't see it.

The drive itself is fine. Once something talks to it directly over USB (with the standard
INQUIRY, TEST UNIT READY, READ CAPACITY, MODE SENSE and READ(10) commands), it answers every
one of them normally. That's what this tool does: with libusb it takes the USB interface away
from macOS's driver (macOS only lets root do this, hence `sudo`) and speaks USB mass storage
itself.

## The drive is virtual: order matters

The drive is not ordinary storage. It is generated by the parent unit's firmware, which
watches what the computer writes:

* **FAT writes are ignored.** The FAT always reads back exactly as the firmware generated it.
* **The root folder is a single buffer.** Writing a root-folder sector replaces it, and every
  root-folder sector reads back that same buffer.
* **Data is only kept if it belongs to a file the firmware already knows about.** Once a
  root-folder entry named `FIRMWARE.BIN` exists with a start cluster and size, data written to
  those clusters is stored in flash at about 0.12 MB/s. Data written anywhere else is accepted at
  full USB speed (13 MB/s) and thrown away, and unused clusters always read back as zeros.

So the copy has to happen in the order Windows Explorer uses: create the directory entry,
allocate the clusters, record the size, then stream the data. Writing the data first (the
"safe" order for normal disks) fails silently. This tool follows the Windows order and adds two
checks:

1. After creating the entry it reads the root folder back and confirms that the parent unit
   registered `firmware.bin` with the right cluster and size. If not, it stops before sending
   any firmware data.
2. It measures the transfer speed over every rolling 1 MB. A parent unit that is really storing
   the image accepts data at roughly 0.12 MB/s. If any 1 MB goes faster than 1 MB/s, that data was
   almost certainly discarded (even if the start of the file was kept), so the tool stops and
   tells you not to press RESET.

Every write must also be fully accepted: if the unit reports bytes it didn't take, or rejects
the data phase while claiming success, the tool stops. Any failure after the first write, including
Ctrl-C or the unit switching off while the tool waits for it to finish, ends with "do not press
RESET".

Because the drive does not return file contents, a read-back check is impossible. Babysense's
own updater doesn't do one either (its log message says the copy "was not read back").

After the copy, Babysense's instructions are: unplug the cable, press RESET, and switch the unit
on. The parent unit then installs `firmware.bin` itself. On our test unit the update also
cleared the camera pairing.

## Where the firmware comes from

Babysense distributes the update only as a Windows app on the Microsoft Store: "Babysense Pro -
Firmware Update" (product `9PNMTNWPRKL5`, package
`Babysense.BabysensePro-FirmwareUpdate_1.0.74.0_x64__sm2jydt73ezre`). It is a .NET 10 WPF app.
Its `BabysenseProFirmwareUpdate.Core.dll` embeds two resources:

* the firmware image `Babysense_pro_software_update_V0207.bin` (32,374,784 bytes, starts with
  `SONiX ST53510A`), and
* a SHA-256 pin for it (`a7254a99579aff09157b724817b5adb5565ab5f53f4724d92dce38b0bf9c2ad1`).

The app finds the parent unit by USB ID `0C45`/`8801` (falling back to the volume label), checks
it's a removable drive with enough free space, and copies the image to the drive root as
`firmware.bin` (the `DeviceIdentification.FirmwareFileName` constant), directly, with no
temporary file.

This tool never runs that app. It downloads the package the same way the Microsoft Store app
does:

1. `displaycatalog.mp.microsoft.com` gives the package name, size and Windows Update category.
2. `fe3.delivery.mp.microsoft.com` (the Windows Update service) returns the download link. Like
   a real Windows Update client, the tool syncs in rounds, reporting the prerequisites it was
   given as installed, until the package appears (two rounds today).
3. The package is downloaded from `*.dl.delivery.mp.microsoft.com`.

The SOAP requests are written from scratch for this project.

## Integrity checks

Microsoft serves Store packages over plain HTTP; its download hosts don't offer working HTTPS.
Windows Update relies on digests for this, and so does this tool:

1. The size and SHA-1 digest of the package come from Microsoft's update service over TLS that
   trusts only Microsoft Root Certificate Authority 2011 (bundled in `babysense_mac/certs`, the
   public root that service uses), so no other certificate authority can vouch for it. The
   download must match both. It's stopped early if it grows past the expected size or takes too
   long, and redirects to any host outside Microsoft's download servers are refused.
2. The package manifest must name Babysense's package identity and Store publisher ID.
3. The firmware's SHA-256 must match the pin inside Babysense's DLL **and** a value hard-coded in
   this tool (`constants.TESTED_FIRMWARE`). A newer, untested firmware is refused unless you pass
   `--allow-untested-firmware`.
4. The privileged (`sudo`) step re-reads the firmware file (refusing symbolic links and files owned
   by other users), re-checks its SHA-256 and enforces the tested list again before sending anything.

The package's own code signature isn't verified, and the SHA-256 pin sits inside the same package,
so it proves integrity rather than origin. On the default path that doesn't matter, because the
firmware must match the tested SHA-256 in this tool. With `--allow-untested-firmware`, authenticity
rests only on Microsoft's SHA-1 digest from the pinned connection; the tool warns when that flag
is used.

## Safety rails in the code

* The USB layer can only send the SCSI commands listed above, plus WRITE(10) and SYNCHRONIZE
  CACHE(10) during an install. Anything else (for example FORMAT UNIT) is refused before it
  reaches the device.
* Writes go through a guard whose allowlist is fixed from the plan before the first write: the
  root-folder sector, the FAT sectors for the new chain in both FAT copies, and the file's data
  sectors. Sector 0 can never be written.
* The `sudo` step runs `/usr/bin/sudo` and Apple's root-owned `/usr/bin/python3` by full path, with
  `-I -B` (no user site-packages, no bytecode files written into your folder). Before asking for
  your password, the tool checks that its own files and the libusb library belong to you (or root)
  and can't be changed by other users. This can't protect against malware already running as
  you; nothing that uses `sudo` can.
* The tool refuses drives that aren't the parent unit, drives that are write-protected or
  non-removable, and drives whose size differs from the tested unit.

## About the `01.00.01.051` entry

The parent unit always shows an empty entry named `01.00.01.051` in its drive. It looks like a
version number, but on our test unit it was identical before and after the V0207 update, so it
doesn't reflect the installed firmware version.
